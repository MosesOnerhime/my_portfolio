# Project and Case Study Standards

## Principle

A portfolio project should prove:

- what was built;
- why it mattered;
- what Moses personally did;
- how it was approached;
- what actually exists now.

A project page is not only a gallery.

## 1. Project-card minimum

A project card should communicate, when verified:

- name;
- category;
- concise description;
- year/status;
- key role/capabilities;
- representative image;
- case-study destination;
- live/source destination if available.

Keep the card concise.

## 2. Case-study header

A strong case-study opening can include:

- project name;
- one-sentence summary;
- project type;
- role;
- timeframe/year;
- status;
- tools/stack;
- team/context;
- live link;
- source link when public.

Only show fields that are true.

## 3. Case-study story

Use the smallest useful structure for the evidence available.

Recommended sections:

### Context
What the project is and why it exists.

### Challenge
What problem/constraint needed to be solved.

### Role
What Moses personally owned.

### Approach / decisions
Important design, engineering, gameplay, product, or creative decisions.

### Implementation
Useful technical or production detail.

### Outcome / current status
What shipped, what works, what was delivered, or what remains in development.

### Reflection
What was learned or what would be improved next, when useful.

## 4. Contribution clarity

For team/internship work, distinguish:

- what the wider project/team did;
- what Moses personally contributed.

Do not imply sole ownership if the source content says otherwise.

## 5. Outcomes

Use only real outcomes.

Valid evidence includes:

- shipped/live product;
- feature completion;
- implemented system;
- deployed website;
- completed internship deliverable;
- documented technical behavior;
- verified adoption/metric if available.

Do not manufacture percentage improvements simply because case-study templates often contain metrics.

## 6. Technical depth

Developer case studies should show enough implementation detail to prove skill without becoming documentation dumps.

Useful examples:

- architecture decision;
- state/data flow;
- backend integration;
- performance challenge;
- realtime system;
- authentication;
- deployment;
- game system;
- responsive architecture;
- key trade-off.

## 7. Creative work

Creative-direction/motion work may use a different evidence structure:

- brief/intention;
- role;
- edit/motion/design decisions;
- software/tools;
- selected frames/video;
- result/published piece.

Do not force a software-engineering template onto creative projects.

## 8. Game work

Game-development work may emphasize:

- gameplay goal;
- player experience;
- systems;
- controls;
- networking/server authority;
- animation;
- camera;
- iteration;
- current development state;
- footage.

Do not disclose private/proprietary implementation content not already intended for the public portfolio.

## 9. Project imagery

Use real evidence.

Images should:

- have intentional aspect ratio;
- reserve layout dimensions;
- include meaningful alt text when they convey information;
- be captioned when context is not obvious;
- open/enlarge only if the interaction is useful;
- remain navigable by keyboard if a lightbox is used.

## 10. Case-study navigation

Each case study should provide:

- clear back-to-work path;
- previous/next or related project when useful;
- contact/engagement next step;
- project live/source links when verified.

Avoid dead-end case studies.

## 11. Repeated links

A grid of visible links all labeled `Case study` may be visually elegant but should have distinct accessible names.

Example:

Visible text:

`Case study`

Accessible name:

`View Drixil Group case study`

Do not add redundant visible copy if an accessible label solves the issue cleanly.

## 12. URLs

Prefer stable, readable case-study URLs.

Do not break existing public URLs during cleanup.

If slugs change for a strong reason, add redirects and update canonical/internal links.

## 13. Confidential work

For internship/client work:

- do not reveal confidential content;
- do not fabricate anonymized results;
- use approved/public artifacts only;
- state constraints clearly when needed.
